date: "2026/7/27"
---

训练代码里写一行 `C = A @ B`，看上去是一件瞬间发生的事：一句话，一个操作，一个结果。实际上不是。从这行代码被解释执行，到 `C` 里真正有一个数字被算出来、躺进内存里，中间要经过一整叠不同的层——四层在 CPU 上，一层在边界上，三层在 GPU 上，每一层只负责一件很窄的事。这篇文章沿着这叠层从上往下走一遍，全程用同一个具体的小例子：`A` 是一个 4×3 的矩阵，`B` 是一个 3×2 的矩阵，`C = A @ B` 是那个 4×2 的结果。

![八层，一次矩阵乘法](blogs/images/matmul-eight-layers.svg?v=1)

## 1. Python：这行代码本身

在这一层，`C = A @ B` 还没有开始做任何算术。`A` 和 `B` 是携带着形状、数值类型、以及"待在哪个设备上"这些信息的对象；这行代码本身是一次用这些信息表达出来的请求——"把这两个东西乘起来"——交给对象下面的机制去处理。到这里为止，还没有任何数据被读取、被相乘、被相加。这一层唯一的工作，是描述这次计算，而不是执行它。

## 2. 框架的 dispatch：判断该走哪一类实现

框架看一眼刚才拿到的这些信息——操作数待在哪个设备上、什么数值类型、什么形状——判断哪一类实现是适用的。同样是"矩阵乘法"，为这种硬件、这种数值类型准备的代码，和为另一种硬件或另一种数值类型准备的代码，是完全不同的两段代码，尽管概念上都叫"矩阵乘法"。这一层的工作就是路由：把请求送到正确的那一类实现那里去，不多做别的事。

## 3. Kernel 选择：挑出适合这个形状的具体方案

在上一层判断出的这一类实现里面，通常不止一种矩阵乘法的具体实现——会有好几种，各自针对不同的形状范围做过调优。其中一种版本可能对我们这个 4×3 乘 3×2 的例子效率很高；同一类方案里另一个为体量大上几千倍的矩阵准备的版本，拿来算这个例子结果照样正确，只是效率差一些。这一层的工作，就是挑出最适合这次具体形状的那一个方案。

## 4. 启动配置：这份工作怎么被切开

到了这一层，问题的形状才第一次真正起作用，而不只是一个描述信息。`C` 一共有 4×2 = 8 个元素，而这一层的核心洞察在于：这 8 个元素原则上可以完全互相独立地被算出来。这一层的工作，是决定怎么把这 8 份独立的工作切成一组一组、大小要匹配目标 GPU 喜欢接收工作的方式，再把这份切分方案和第 3 层选好的具体方案打包在一起。

## 5. 驱动 / 队列：CPU 交接出去

上面几层选好的启动方案和具体实现，被驱动翻译成一次请求，放进属于这块 GPU 的队列里。这正是这一整叠层一直在铺垫的那个边界：这一层往上，都是在 CPU 上运行的软件，描述一次计算；这一层往下，才是这次计算真正发生的地方。而且关键的是，CPU 到这里就先不管了——它不会等这个队列被处理完。它立刻把控制权收回来，去发起接下来要做的任何事。

## 6. GPU 调度：工作遇上计算单元

GPU 有自己独立于 CPU 的调度逻辑，从队列里取出这次请求，把第 4 层打包好的那些工作，分发给它众多板载计算单元里当前空闲的那些。对我们这个只有 8 个元素的小例子来说，这一步几乎是瞬间完成的；但如果是一次有几百万个独立元素的矩阵乘法，真正要做繁重工作的正是这一层：把这么大量的独立工作，摊到所有能用来处理它的硬件上。

## 7. 计算单元内部执行：线程在做点积

真正的算术在这一层发生，这个具体例子也在这一层最能派上用场。`C` 的 8 个元素里，每一个都恰好是 `A` 的某一行点乘 `B` 的某一列——8 次完全独立的点积，彼此之间没有任何数据依赖。被分配到其中一个点积的线程，从内存里读出对应的那一行 `A` 和那一列 `B`，走一遍点积需要的那一串乘加运算，把算出来的那一个数字写进 `C` 对应的内存位置。其他每一个线程，在同一时间，做的都是同样类型的工作，只是换了一对行列。

![为什么矩阵乘法天然适合并行](blogs/images/matmul-thread-parallel.svg?v=1)

这也正是矩阵乘法天生适合这类硬件的原因：底层的数学根本不需要靠什么巧妙的手段被硬拆成独立的几份。它本来，结构上，就是一大堆一模一样、互相独立的工作——每个输出元素对应一次点积——而这正是这类硬件生来就是为了跑这种形状的负载而存在的。

## 8. 完成，以及回去的路

等所有线程都写完各自的那个元素，`C` 就完整地躺在 GPU 显存里了。但这次"完成"本身什么都不会主动触发——没有任何东西强迫 CPU 去注意到它、或者等它。如果训练代码的下一行还要用 `C` 去做另一次 GPU 计算，这一层什么都不需要发生：那次计算会用同样的方式被发起，接在这次后面，GPU 按顺序从队列里依次处理两个。只有当确实有什么东西需要这个结果的时候，CPU 才会真正停下来等——比如要把这个值打印出来，或者要把结果转换成一个普通的、待在 host 侧的数字，或者程序里任何一个"没有这个真实答案就没法往下走"的点。而且因为结果躺在 GPU 显存里，满足这个需求还要再多一次搬运：把 `C` 里相关的那部分数据拷回 CPU 内存，Python 才能像对待一个普通数字那样去用它。

## 这八层加起来是什么

四层 CPU 侧的软件，一层边界，三层 GPU 侧的执行，再加上一条只有下游真的问起结果时才会走的返回路径。就算是这么小的一个例子——真正的算术只是三个数长度的八次点积，几乎不算什么——这八层全都参与了这一次 `C = A @ B`。边界以上的这几层，花的代价基本上和矩阵是很小还是很大没什么关系，这也是为什么真实的训练代码会尽量让每一次发起的计算覆盖尽量多的实际运算量：为了一次能让 GPU 持续忙很久的计算，走一趟这八层是值得的；为了一次算不了多少东西的计算，反反复复走这八层，就很不划算了。（[GPU 那篇文章](#/blog?id=gpu-field-guide-for-dl) 更深入地讲了第 6、7 层在负载不是 8 个元素、而是几百万个元素时具体是什么样子。）
