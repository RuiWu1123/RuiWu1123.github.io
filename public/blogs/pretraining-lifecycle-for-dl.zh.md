大部分讲大模型训练的材料，只站在一条线的一侧。讲训练算法的材料基本只在模型内部打转：前向、loss、梯度、更新规则，完全不涉及这些计算到底是在哪里发生的。讲硬件和系统的材料基本只在模型下面打转：显存、互联、kernel 调度，完全不涉及一个 batch 的文本一开始是怎么到那儿的。这篇文章讲的是中间那条线，把两头接起来：从磁盘上一个原始文本文件出发，到最终训练好的参数被写回磁盘上另一个文件，中间到底按顺序发生了什么。文章刻意不涉及具体框架、具体硬件、具体数字——这些每年都在变。不变的是这条流水线本身的形状，这篇文章讲的就是这个。

![完整的闭环：从磁盘到磁盘](blogs/images/pretraining-lifecycle-loop.svg?v=1)

## 1. 从磁盘上的文本到一个 token id 的 batch

训练数据一开始是存储里的文件——纯文本，规模看这次训练的需要。在任何数据到达 GPU 之前，一个 CPU 侧的进程会读取这些原始文本的一块一块，跑一遍 tokenizer：一个固定的映射，把文本变成一串从固定词表里取出来的整数 id。这些 id 序列会被截断或者拼接到一个固定长度，然后固定数量的这种序列会被堆叠成一个 batch——一个二维的整数网格，若干条序列乘以一个序列长度。

这一整套过程都不涉及 GPU。它是磁盘 I/O 加 CPU 侧的字符串处理，相对于接下来要发生的事情来说很慢，这也正是它不会"现用现做"的原因。实际情况是，这一步会在后台持续跑，始终比训练当前实际需要的进度提前准备好一个或几个 batch，这样等上一个 batch 被消耗完的时候，一个刚准备好的 batch 已经在 CPU 内存里等着了。对后面的内容来说重要的是这个结构性事实：batch 准备是一个 CPU 和存储主导的过程，它和下面要讲的一切是**并行**发生的，而不是排在它们前面依次发生。

## 2. 把一个 batch 搬到 GPU 上，以及模型本身已经待在哪里

一个待在 CPU（host）内存里的 batch，GPU 没法直接对它做计算；它必须先被实实在在地拷贝到 GPU 自己的（device）内存里，经过连接两者的某种通路。这次拷贝每个 batch 发生一次，每一步都要发生一次，贯穿整个训练过程——每次新数据要到达 GPU，都要交这么一笔小额但反复发生的"税"。

模型参数走的是完全不同的模式。训练开始之前，参数先被初始化（用某种随机化方案），然后被拷贝到 GPU 的 device 内存里，只拷贝这一次。从那之后，它们就一直常驻在那里，贯穿整个训练——一步一步原地修改，从来不像 batch 数据那样每一步都要从 host 重新搬过来。（如果模型大到一张 GPU 的显存根本装不下，这是一个真实的约束，第 5 节会回来讲。）训练过程中流经 GPU 显存的这两种数据流，长得完全不一样：batch 数据每一步都新到一批，用完就丢；参数只到达一次，原地被修改，待满整个训练过程。

## 3. 桥梁：一行训练代码的执行到底发生了什么

这一节要解开的问题是这样的：训练代码里一行像 `output = compute(a, b)` 这样的语句，是在 CPU 上执行的——Python 解释器在 CPU 上跑这一行，和其他任何一行代码没有区别。但真正的计算却应该发生在 GPU 上。这两件事只有在你不再把这行代码看成"执行了一次计算"，而是看成"发起了一次计算"的时候，才能对上。

![CPU 发起调度，GPU 异步执行](blogs/images/cpu-dispatch-gpu-execute.svg?v=1)

在任何真正的计算发生之前，有三件事按顺序发生，而且完全发生在 CPU 这一侧：框架看到这个高层操作，挑出适合它的具体底层实现；一次驱动层的调用把这个底层操作打包成一条指令；这条指令被放进属于 GPU 的一个队列里。关键的一点是，CPU 不会坐在那里等这条指令跑完。它立刻把控制权收回来，接着去发起下一条指令，除非程序后面马上就要用到这次计算的结果。

```python
def training_step(batch, model):
    output = model.forward(batch)   # 发起调度——这次调用在 GPU 跑完之前就返回了
    loss = loss_fn(output, batch.labels)
    loss.backward()                 # 同样是发起调度，不是在这里执行
    optimizer.step()                # 同样是发起调度
    # 这个函数返回的时候，CPU 已经往 GPU 的队列里塞进了一长串指令；
    # GPU 可能还在慢慢处理这些指令
```

GPU 这一侧独立地、异步地运行：它按顺序从自己的队列里取出指令，对每一条指令，把底层的计算展开成海量的并行线程，分发到 GPU 内部众多独立的计算单元上，并发执行。（[GPU 那篇文章](#/blog?id=gpu-field-guide-for-dl) 讲了一条指令真正到达硬件之后发生的事情，比这篇文章需要的深入得多。）

值得留住的心智模型是：两条时间线同时在跑。CPU 这条时间线，是一串很快的发起动作。GPU 这条时间线，是从队列里慢慢消化掉的、相对更慢的真实计算积压。只要 CPU 发起指令的速度始终快过 GPU 消化这些积压的速度，两条时间线就一直保持解耦，GPU 也就永远不会闲下来等 CPU 递给它下一件事做。正是这整套机制，让"代码在跑"和"计算在发生"变成了两件不同的事——发生在不同的时间，不同的硬件上。

## 4. 一个训练 step：forward、backward、update

一个训练 step 里每一行涉及计算的代码，都是第 3 节讲的"发起调度、异步执行"这套模式，被串联着重复了非常多次。把这些一次次的发起动作串成"一个训练 step"的，是一个严格的顺序，由硬性的数据依赖强制规定：forward 必须先产出结果，backward 才能算出任何东西；backward 必须先产出梯度，update 这一步才能用上它们。

forward 把这个 batch 推过模型的一整串操作，产出一个预测，再从这个预测算出一个 loss 值。从机制上看，这是一层接一层、同样那几种操作类型的大规模重复——大部分是大型矩阵乘法，加上少数几种其他结构化操作——每一个都按第 3 节讲的方式被发起、被执行。

backward 算的是每个参数对这个 loss 贡献了多少：也就是梯度。forward 跑的时候，框架会一直记录哪次计算依赖了哪次计算；backward 把这套依赖关系倒过来重放一遍，发起的本质上是和 forward 同一类的大型矩阵计算，只是在模型里反向传播。

update 这一步再用这些梯度，把每一个参数都调整一个小的量。这部分涉及的总计算量比 forward 或 backward 小得多，但走的是完全相同的发起调度机制——只不过是直接作用在每一个参数上，而不是作用在流经网络的激活值上。

理解这里的结构性内容，不需要过一遍底层的数学：一个训练 step 不是三种不同性质的事情。它是第 3 节那套"CPU 发起、GPU 执行"的机制，被重复了海量次数，作用在恰好分成三个阶段、彼此之间有硬性顺序的计算上。

## 5. 当一张 GPU 不够用

模型参数、单个 step 的这批数据、forward 过程中产生的中间激活值，这三样东西必须同时装进 GPU 显存，而且这三者都会随着模型规模或数据规模变大。超过某个点之后，它们就是没办法都装进一张 GPU 里，唯一的出路是把参数、数据或者激活值中的某一样，切分到多张 GPU、乃至多台机器上去。（[分布式训练那篇文章](#/blog?id=distributed-training-for-dl) 详细讲了具体怎么切分；真实的训练任务通常会同时用上不止一种切法。）

这里重要的是，切分之后，第 3、4 节搭起来的这套图景发生了什么变化：每张 GPU 依然在跑一份自己的、完全一样的"发起调度、执行计算"循环，只是作用在被分配到的那一部分参数、数据或激活值上。大多数时候，一张 GPU 自己的 CPU 侧进程在发起指令，这张 GPU 在执行这些指令，和其他任何一张 GPU 在做什么完全无关。

但不是永远如此。在某些具体的时间点上——具体是哪些点，取决于切分的方式——一张 GPU 下一步要做的计算，依赖一个当前存在于另一张 GPU 上的结果。到了这个点，涉及的这几张 GPU 必须先通信：把各自算出来的部分结果发给对方、合并起来，然后才能继续往下走。这种通信可能发生在同一台机器里的多张 GPU 之间，也可能发生在通过网络连接的、完全不同的机器之间；具体方式不一样，但在整个流程里扮演的结构性角色是一样的。

多卡训练一个 step 的节奏因此变成：独立计算，然后是一个同步点，然后又是独立计算，如此反复，一个 step 内部要重复多少次，取决于具体的切分方案。第 3、4 节讲的机制本身没有任何变化——只是现在这套机制在很多张 GPU 上并行地跑，在计算本身要求同步的地方，多了几次必须完成的握手。

## 6. 循环

第 1 到第 5 节讲的都是一个 step 内部发生的事：一个 batch，在 CPU 上准备好，搬到 GPU 上，通过"CPU 发起、GPU 执行"的指令依次跑完 forward、backward、update，在需要的地方跨 GPU 同步。训练一个模型，就是把这整套流程原样重复非常多次——通常是数以万计次。

这也是为什么第 1 节讲的流水线细节，不只是一个效率上的注脚，而是结构性的：只有当上一个 step 的计算刚跑完、一个刚准备好的 batch 就已经在那里等着，这个循环才能一直转下去。这意味着 CPU 侧读取、tokenize、打包 batch 的这个过程，必须在整个训练期间持续运行——和 GPU 侧的计算循环保持同步，但又和它彼此解耦。

## 7. 闭合这个循环：回到磁盘

GPU 显存不是持久存储。管理这张 GPU 的进程一旦因为任何原因停下来，当前显存里的东西就没了。所以要定期把参数当前的状态——连同恢复训练所需要的其他一些记录信息——搬回去：从 GPU 显存搬到 CPU 内存，再从 CPU 内存写到持久存储里。这就是一次 checkpoint，从结构上看，它正好是第 2 节讲的那次搬运的反向操作，方向相反，频率低得多，不是每个 step 都发生。

训练会一直在第 3 到第 6 节这套流程里循环，直到达到某个预先设定的终止条件——固定的 step 数、固定的数据消耗量，或者别的什么目标。到了那个点，产出每一次中间 checkpoint 的那套"GPU 到 CPU 再到磁盘"的搬运，会最后再发生一次，这次写出来的，才是整个过程真正的产物：训练好的模型参数，躺在磁盘上的一个文件里。

这就闭合了这篇文章开头提出的那个循环。训练从磁盘上一个文件里的原始文本开始，到磁盘上另一个文件里的参数结束。中间的一切——tokenize、打包 batch、把数据搬上 GPU、从 CPU 发起指令、把它们作为海量并行计算异步地在 GPU 上执行、在切分了工作的地方让多张 GPU 保持同步——是同一个循环，被重复了数以万计次，直到它产出这整个过程存在的目的：那个文件。
