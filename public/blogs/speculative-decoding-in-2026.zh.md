从一个大模型里生成一个 token，需要把模型的全部权重读一遍，真正做的运算却很少。batch size 为 1 时，GPU 大部分时间在等内存，算力单元基本闲着。speculative decoding 的机会就在这个失衡上：既然瓶颈是访存而不是计算，那么一次验证多个 token 的代价，并不比验证一个高多少。

于是有了这样一个思路。先用一个轻量的 drafter 猜出接下来的 γ 个 token，再把这一整段交给大模型做一次前向。这次前向会给出每个位置上的分布，据此对每个候选 token 逐一判断接受还是拒绝。每接受一个，就省下了本该为它单独跑的一次前向。

真正让它站得住的不是这个思路本身，而是存在一种采纳这些猜测的方式，能让输出分布**精确地**保持不变。这个结论来自两篇同期独立完成的工作，ICML 2023 上的 [Leviathan et al.](https://arxiv.org/abs/2211.17192) 和 DeepMind 的 [Chen et al.](https://arxiv.org/abs/2302.01318)，两边都报告了约 2–3 倍的加速，输出则与原模型自己解码的结果完全一致。此后所有的工作，本质上都是在把"猜"这一步做得更好。

## 一、这条规则，以及它换来什么

记 `p` 是 target 在某个位置上的分布，`q` 是 drafter 在同一位置上的分布。我们要的是一套流程：有时候接受 drafter 的提议，有时候拒绝，但必须满足一个硬约束，就是最终输出的 token 严格服从 `p`。在这个约束下，我们希望接受得越频繁越好，因为省下来的时间全部来自接受。

这两条要求摆在一起，答案几乎是被逼出来的。在词表里任取一个 token `x`，记 `A(x)` 为"这一轮既提议了 `x`、又接受了它"的概率。这里要留意，`A` 是定义在整个词表上的函数，不是一个数：一轮确实只抽出一个 token，但在抽之前，词表里每个 token 都各有一份概率成为那个被提议并被留下的。所以把 `A` 在整个词表上求和，得到的是"这一轮最终以接受收场"的概率，也就是 acceptance rate α。

`A(x)` 从上面受两条限制。这一轮要接受 `x`，前提是它提议了 `x`，而提议 `x` 的概率是 `q(x)`，所以 `A(x) ≤ q(x)`。另一条来自那个硬约束：`x` 被输出有两条路径，接受是其中一条，另一条是被推翻之后重采，因此 `A(x)` 不可能超过 `x` 被输出的总概率，而约束把这个总概率钉死在 `p(x)`，于是 `A(x) ≤ p(x)`。两条合起来，每个 token 上都有 `A(x) ≤ min(p(x), q(x))`，在词表上求和，接受率就有了上限：

$$
\alpha \;=\; \sum_x A(x) \;\le\; \sum_x \min(p, q) \;=\; 1 - \mathrm{TV}(p,q), \qquad \mathrm{TV}(p,q) = \tfrac{1}{2}\sum_x |p - q|
$$

最后那个等号值得自己推一遍，两行就够。因为 `min(a, b) = (a + b − |a − b|)/2`，在词表上求和便得到 `Σ min(p,q) = (1 + 1 − Σ|p − q|)/2 = 1 − ½Σ|p − q|`，末尾这个量正是 total variation 距离的定义。那个 ½ 的来历是：`Σ|p − q|` 把每一处分歧数了两遍，`q` 在哪里给多了，就必然在别处给少了同样多，多出来的和缺掉的都会进到这个和里。折掉一半，剩下的正是把 `q` 搬成 `p` 需要挪动的概率质量。所以这个等式说的事情很朴素：`Σ min(p, q)` 是两个分布已经重合的部分，TV 是没重合的部分，两者加起来是 1。无损方案能做到的最好情况，就是把已经重合的那部分原样接受下来。

这个上限约束的是**任何**保持 `p` 不变的方案，不只是眼下这一个。再聪明的设计也不可能超过它。

规则本身是这样：

```python
x = sample(q)                            # the draft proposes a token
if uniform() < min(1, p[x] / q[x]):      # the target checks it
    emit(x)
else:
    emit(sample(normalize(maximum(p - q, 0))))
```

让这个上限真正被取到的，正是 `min(1, p[x]/q[x])` 这个接受概率。一个 token 以 `q(x)` 的概率被提议，再以 `min(1, p(x)/q(x))` 的概率被留下，于是它最终存活的概率是 `q(x)·min(1, p(x)/q(x)) = min(p(x), q(x))`，恰好等于上限本身。而且这不是在总量上凑出来的，是每个 token 各自都达到了自己那一份上限。

上限一旦达到，剩下的部分也就随之确定了。接受这条路径已经吐出了 `min(p, q)`，那么还欠 `p` 的就是 `p − min(p, q)`，也就是 `(p − q)⁺`，这里的上标 ⁺ 表示逐分量取 `max(p − q, 0)`。这个截断不是为了好看。在 `p < q` 的那些 token 上，接受路径已经给足了 `min(p,q) = p`，正好是 `p` 要的全部，所以那里的缺口是零而不是负数；缺口只出现在 drafter 给少了的那些 token 上。这部分缺口的总量同样没有自由度：`Σ(p − q)⁺ = 1 − α`，恰好就是拒绝发生的概率。所以在拒绝时，从归一化后的 `(p − q)⁺` 里采样，两条路径加起来就是 `min(p,q) + (1−α)·(p−q)⁺/(1−α) = p`。没有任何可调的余地。

有两种错法值得点名，因为都很诱人。不做截断、直接对 `p − q` 归一化，不是"效果差一点"，而是根本没定义：`Σ(p − q) = 0`，你会除以零。另一种是被拒之后直接从 `p` 重采：这是最顺手的猜法，会把 `q` 已经覆盖过的部分重复计一遍。拿 `p = (0.6, 0.4)` 配 `q = (0.2, 0.8)` 算一下：α = 0.6，residual 是 `(0.4, 0)`，归一化后是 `(1, 0)`，两条路径加起来正好还原 `(0.6, 0.4)`。换成从 `p` 重采，得到的是 `(0.44, 0.56)`，跑四十万次模拟实测是 `(0.4405, 0.5595)`。在两个 token 上错得一眼可见，但同样的偏差放到十万词表上，会非常容易被漏掉。

有必要挑明：这一整套并不是 speculative decoding 的原创。让两个分布共享 `min(p, q)`，这是概率论里的 **maximal coupling**，而 `1 − TV` 是它标准的最优结论。2023 那两篇的贡献在于把它用到这里，外加那个"一次定胜负"的结构：经典的 rejection sampling 会一直从 `q` 重抽直到某次被接受，重抽次数没有上界；而 coupling 只给一次机会，失败就退到 residual，于是每个位置恰好抽一次就收工。

![The accept and reject rule](blogs/images/specdec-accept-rule.svg?v=1)

绿色是直接接受的那部分 `min(p, q)`，加起来就是 acceptance rate α = 0.66。蓝色是 `(p − q)⁺`，也就是 residual 要补的那部分，而它不只是跟 total variation 有关，它就等于 total variation：`Σ(p − q)⁺ = ½Σ|p − q| = 0.34`。这张图画的就是上面那个恒等式。`α = 1 − TV(p, q)` 这个闭式在原论文里是推论 3.6。换句话说，一个有一半 token 能被接受的 drafter，就是一个分布与 target 相距 0.5 个 TV 的 drafter，与它用什么架构无关。

"这是精确的"这类结论读的时候很容易一带而过，代码里又很容易出微妙的错，所以值得亲眼验一遍。我在八个 token 上取了一个 target 分布 `p`，故意配一个与它 TV 距离 0.34 的劣质 `q`，跑了两百万次单 token 的 speculative 步。

![Empirical distribution after two million speculative steps](blogs/images/specdec-lossless.svg?v=1)

drafter 的偏差肉眼可见，众数落在了错误的 token 上。输出却没有：实测输出与 `p` 的 TV 距离是 0.00046，而两百万次采样的噪声地板约为 0.00071。drafter 自身那 0.34 的误差不是被削小了，而是完全消失了。这正是 speculative decoding 在一堆推理优化里显得特别的地方。量化和剪枝都是拿质量换速度，而它什么也不换：drafter 差，损失的是速度，不是正确性。

接下来算收益。一轮里 drafter 产出 γ 个 token，target 用一次前向把它们全部验证。这一次前向之所以能同时给出 γ 个位置各自的分布，是因为草稿 token 被当作一整条序列喂进去，配上 causal mask，每个位置只看得见它前面的部分。训练时给整条序列一次性打分，用的也是同一套 teacher forcing。

有一个后果值得单独说，它解释了 α 为什么这么要紧。第 k+1 个草稿 token，是在"第 k 个 token 是 x"这个前提下产出的；target 在同一次前向里算出的第 k+1 个位置的分布，也同样以此为前提。所以位置 k 上的一次拒绝，代价并不是一个 token：后面每一个草稿，以及这次前向已经算好的后面每一个分布，依据的都是一段不再成立的前缀。一次拒绝就把这一轮剩下的全部作废，这也正是产出呈几何形态而不是线性的原因。

第一次拒绝若发生在第 k 个位置，这一轮产出 k+1 个 token：k 个被接受的，加上那个从 residual 重采的替补。如果 γ 个全部通过，产出 γ+1 个，多出的那个采自 target 在最后一个位置上的分布，而这次验证前向已经把它算出来了。在原论文声明的简化假设下（各位置接受与否独立同分布、接受率为 α），一轮的产出服从一个截断几何分布，期望是 `(1 − α^(γ+1))/(1 − α)`，这个式子在我测过的每一组 α 和 γ 上都对得上，差距在采样噪声以内。α = 0.75、γ = 4 时，21 个 token 只用了 6 次 target 前向，而不是 21 次：

![Target forward passes, autoregressive versus speculative](blogs/images/specdec-timeline.svg?v=1)

要注意这张图只统计了 target 的前向次数。作为机制示意这是最诚实的口径，但当成加速比看就偏乐观了，因为 drafting 本身有成本。

所以把这笔成本放回去。记 `c` 是一次 draft 前向相对一次 target 前向的成本占比，墙钟加速就是

$$
\text{speedup} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}
$$

取舍就在这里。γ 调大，分子的增长越来越慢（第 i 个 draft token 只有在它前面全部被接受时才算数），分母却是线性增长的。于是存在一个最优的 γ，并且它随 α 移动：

![Speedup against draft length for several acceptance rates](blogs/images/specdec-speedup.svg?v=1)

α = 0.9 时最优的草稿长度是 7，约 2.4 倍；α = 0.5 时最优长度只有 1，约 1.25 倍，再长反而更慢。真正该盯的数字是 acceptance rate，而不是 drafter 的大小：α 既决定了收益的上限，也决定了 γ 能开到多大。

顺带纠正一个流传很广的说法：drafter 得比 target 快十倍以上才划算。推论 3.9 说的其实是，只要 **α > c**，就必然存在某个 γ 能带来提升。按常见的 α 在 0.6 到 0.8 计算，drafter 只需要比 target 快 1.3 到 1.7 倍，而不是常被引用的十倍到三十倍。同一篇论文的 Table 4 里就摆着一个 c = 0.11 的配置，drafter 只快约九倍，照样拿到 1.7 到 2.2 倍。已发表的设置基本落在 c ≈ 0.02–0.13，而且两篇原始论文谈甜点区用的都是参数量，不是延迟比。

## 二、drafter 怎么设计

上面一直把 drafter 当成一个产出 `q` 的黑盒。既然真正起作用的只有 α 和 c 两个量，那么每一种 drafter 设计都是这个平面上的一个点，把平面画出来最直观：

![The design space of drafters](blogs/images/specdec-design-space.svg?v=1)

虚线是 α = c。两个箭头是所有人手里仅有的两根杠杆：往上推，让 drafter 更常猜中；往左推，让单次 draft 的成本更低。后续工作几乎每篇都在拉其中一根，做得好的那些则会注意到，这两根杠杆并不彼此独立。

最早的做法是拿同系列里一个更小的模型来当 drafter。它不用改 target，任意一对模型都能搭配，但前提是手上正好有一个在相似数据上训过的小模型，而且 α 完全由这一对模型决定，没有额外的提升手段。它的问题在于：一个独立的模型必须从零重建上下文，而 target 内部本来就已经把这段上下文编码好了。

于是主线就把独立的小模型换成了一个读 target 内部状态的 head。EAGLE 让一个小的自回归 head 以 target 的 hidden feature 为条件（最初的版本取倒数第二层的 hidden state，EAGLE-3 则融合了低、中、高三层），相当于借用 target 自己对上下文的理解去猜，而不是让 drafter 从头建立一份更弱的理解。这纯粹是在拉高 α，而之所以可行，是因为那些 feature 本来就已经算出来了，所以这个 head 可以做得极小。

还有一类转而去压 c，具体怎么压，公式里一眼就能看出来。如果 γ 个 draft token 得靠自回归一个个产出，那分母里的 `c` 其实是 `γ · c_单次`，于是不管 drafter 多好，最优的 γ 都上不去。并行 drafter 把这个耦合打断了：一次前向出一整块，分母于是从 `1 + γ·c_单次` 变成 `1 + c_整块`，彻底不再依赖 γ。把 γ 调大在分母那边就不再有代价，上面那条曲线的最优点会因此大幅右移。这就是这一族方法的全部意义，而如果没意识到 γ 原本出现在公式的哪一项里，这一点是看不出来的。[DFlash](https://arxiv.org/abs/2602.06036) 用的是一个以 target 上下文特征为条件的小 block diffusion 模型，这个选择很自然，因为 diffusion 本来就是跨位置并行的。

还有一类完全不做训练。SuffixDecoding 在 prompt 和历史输出上建一棵后缀树，靠匹配产出草稿，`c` 接近于零，位于这个平面的最左端。它的 α 则完全取决于工作负载：在开放式文本上几乎没有用；到了 agentic 这类场景，模型会大段引用自己先前的输出，效果好得出人意料。

## 三、drafter 怎么训练

把 α 往上推，本质上是个训练问题，而这里最主要的失败模式只有一个：训练 drafter 用的分布，和它推理时真正面对的分布对不上。

朴素的目标函数是：给一段真前缀，让 draft head 预测 target 的下一个 token。可推理时 drafter 要连着往前跑好几步，每一步依据的是**它自己**先前的猜测，而那些猜测有时是错的。到第三个位置上，它被要求续写的是一段训练里从没出现过的前缀。这就是普通的 exposure bias，表现出来就是接受率沿着块内位置往后递减。

[EAGLE-3](https://arxiv.org/abs/2503.01840) 用作者称为 training-time test 的办法修它：训练时就把多步 drafting 的过程模拟一遍，让这个 head 面对的是它推理时真会遇到的分布。同一篇还做了第二个改动，放弃预测 feature、改成直接预测 token，并报告这个组合让 drafter 能持续从更多训练数据里获益，而原来那种预测 feature 的形式做不到。

并行 drafter 的问题不同，但根源相通。既然块内每个位置都是独立预测的，就没有任何机制阻止第 4 个位置与第 3 个位置自相矛盾，于是越靠近块尾，一致性越差。这条衰减曲线的形状，比看上去更要紧：

![Acceptance along the block](blogs/images/specdec-suffix-decay.svg?v=1)

一轮的产出是 `1 + Σ_k Π_{i≤k} α_i`，这正是第一节那个期望产出的一般形式：把所有 α_i 取成相同的值，它就退回 `(1 − α^(γ+1))/(1 − α)`。既然是一串**连乘**，靠前的位置权重就远大于靠后的，尾部一路下滑造成的损失，比"平均接受率"这个数字暗示的大得多。上图三条曲线里，衰减那条的平均接受率并不低，产出却只有每轮 3.81 个 token，而平坦那条是 4.33。

修这条衰减正是 [DSpark](https://arxiv.org/abs/2607.05147) 做的事：在并行主干之上叠一个极轻的序列 head，把块内位置之间的依赖重新注回去。它的 Markov 变体是把一阶转移矩阵做低秩分解，实际做的事情就是在并行模型给出的边缘 logits 上加一个秩为 r 的偏置，用来重建一部分联合分布。把衰减压平比把平均值抬高收益更大，这也是上图第三条曲线能到 5.32 的原因。

## 四、verification 怎么设计

verification 这一步，三年来一直是一条不加区分的固定规则，如今剩下的优化空间，有相当一部分就在这里。

首先，没什么规定说草稿必须是一条链。如果 drafter 在同一个位置上给出好几个候选，target 完全可以在同一次前向里把它们一并验证，反正这次前向本来就是访存受限的。验证规则可以按递归的方式自然推广。先拿第一个候选对着 `p` 试。如果被拒，此刻仍然欠着的分布就是 residual `p₁ = (p − q)⁺ / Σ(p − q)⁺`，那就拿第二个候选对着 `p₁` 用同样的规则试；再失败就得到 `p₂`，依此类推。每一轮都是把同一个 maximal coupling 施加在尚未被兑现的那部分质量上，所以整个复合过程最终仍然精确落在 `p` 上。多给候选换来了更高的接受率，却没有引入偏差，因为每失败一次，coupling 的目标分布就被更新一次，而不是拿旧的再用一遍。

![Chain versus tree, and acceptance against candidate count](blogs/images/specdec-tree-verify.svg?v=1)

还是同样的 p 和 q，一个候选时接受率 66%，六个候选时 87%。这里最反直觉的是：它**依然是精确无损的**。多给几个候选并不会让输出有偏，只是更少退回 residual。这就是 tree drafting 的思路。EAGLE-2 又往前推了一步，让树的形状随上下文变化，把候选预算花在 drafter 最不确定的位置上。

再往下，验证长度也不必是个常数。只有大概率能被接受的长草稿才值得验证；而在高负载下，target 的 batch 容量本身就是稀缺资源，speculation 正在和真实请求争夺它。DSpark 的另一半就是按请求调度验证长度，依据是一个校准过的前缀存活概率估计，加上引擎的吞吐画像，好让繁忙的服务器不再把 target 的容量花在多半会被丢弃的 speculation 上。

还有一件不太舒服的事实：验证规则是可以放松的，放松就能更快。[Medusa](https://arxiv.org/abs/2401.10774) 在 target 上挂若干个解码 head，验证用的是它称为 typical acceptance 的做法：target 给这个 token 的概率只要越过一个跟熵有关的阈值就接受，也就是 `p(x) > min(ε, δ·exp(−H(p)))`，论文里 ε 从 0.01 扫到 0.25，并取 δ = √ε。论文对这笔交易是挑明了说的，不是含糊过去："我们确认，通常并没有必要匹配原模型的分布"，附录里还有一句更直白的："我们并不坚持输出与语言模型分布之间的精确对应"。它留了一个可调的阈值，调大就是用更激进的接受换速度。

值得知道的是，开山那篇先到过这里，然后选了相反的方向。它的附录 A.5 描述的正是这样一种松弛，取名 lenience，并报告它在 T5-XXL 上能到 5 倍而严格版是 3 倍，然后把它隔离了：全文其余部分一律用最严格的算法，不允许任何 lenience。同一个想法，一篇把它当成需要隔离的例外，另一篇把它设成默认。温度为 0 时这个区别就消失了，因为 typical acceptance 会退化成贪心。但"无损"这个词确实得读仔细：它是关于那条拒绝规则的精确断言，改了规则的方法并不自动继承这个断言。

## 五、把它塞进引擎

到这里为止讲的都是孤立的一个请求。把 drafter 放进真实的服务引擎，会打破引擎原本已经安排妥当的好几件事。

先是 batch 的形状。正常的 decode 步喂给 target 的是 B 条序列、每条一个 token。verification 喂的是 B 条序列、每条 γ+1 个 token；草稿要是树而不是链，那就是树有多少节点就多少个。这意味着每一轮的 kernel 形状都在变：CUDA graph 要求形状固定，chunked prefill 又在争同一份 token 预算，两边都会冲突。

接着是 attention mask。验证一条链很容易，因为草稿 token 是因果有序的，普通的 causal mask 就够。验证一棵**树**就不行了：同一个位置上的两个兄弟候选绝不能互相看见，但两者都必须看见共同的祖先。这需要一个自定义 mask，把树的拓扑编码进去：

![Causal mask versus tree mask](blogs/images/specdec-tree-mask.svg?v=1)

在这棵五个节点的树上，普通 causal mask 会多放行四对，让 `b` 看见它的兄弟 `a`，让 `d` 同时看见 `b` 和 `c`。这里每一处都会让某个候选以一个不在自己路径上的 token 为条件，从而在不报错的情况下破坏验证的正确性。按树的拓扑把正确的 mask 造出来，正是 [SpecInfer](https://arxiv.org/abs/2305.09781)（ASPLOS '24）真正的系统贡献，它提出的 tree-based parallel decoding 让一整棵 token 树能在一次前向里验完，报告分布式推理 1.5–2.8 倍、offloading 推理 2.6–3.5 倍。

还有 KV cache。最终被拒的 draft token，KV slot 已经写进去了，引擎必须把这些 slot 回滚，而且回滚时不能扰动 batch 里其他序列的 block table。用分页缓存的引擎在这件事上占了便宜，因为回滚只是改 block table 里的记账，不涉及数据搬运。这算是分页的一个不太被提起的好处。

落到实处，两个开源引擎收敛到了类似的结构。[vLLM](https://docs.vllm.ai/en/stable/features/speculative_decoding/) 在 `speculative_config` 后面暴露一个 proposer 接口，把 `ngram`、`suffix`、`draft_model`、`mtp`、`eagle3`、`dflash` 都做成一等方法，另外它的测试集里有一个 rejection sampler 收敛测试，检查采样器的输出分布是不是真的跟 target 对得上。这里也正是第一节那点算术在工程上最容易出事的地方：当 `p` 和 `q` 非常接近时，`Σ(p − q)⁺` 是个很小的数，在 fp16 下拿它做归一化，恰恰是那种会悄无声息破坏无损保证的操作。那个测试就是第一节那条承诺落到工程上的形态：无损是一条可以写成回归测试的性质，而认真对待它的引擎会真的去写。

SGLang 则是让 [speculative worker](https://docs.sglang.ai/advanced_features/speculative_decoding.html) 和它的 overlap scheduler 一起跑，后者的目的是把 CPU 上的调度工作藏到 GPU 执行的背后。这个组合确实难做，而它的限制是写在文档里而不是藏着的：overlap 目前只支持 `--speculative-eagle-topk 1`，也就是链的情形，更宽的树还在路线图上。这一点很说明问题：tree drafting 和 scheduler overlap 填的是 GPU 的同一段空闲时间，于是互相冲突。

最后一块是知道什么时候该收手。既然 speculation 是在跟真实请求抢 target 的 batch 容量，那么负载上来时引擎应该能把它关掉。vLLM 可以按 running queue 的长度把 proposed length 降到零，不过按一个[未关闭的 issue](https://github.com/vllm-project/vllm/issues/25112) 的说法，自动版本并不总能在配置的 batch size 处如期关闭。这和 DSpark 的 confidence scheduling 是同一个思路，只是从运维一侧提出的：负载低于某条线时，speculation 的成本几乎可以忽略；高于那条线，它就是在从本来也能被服务的请求那里抢容量。

## 六、收益会跑到哪里去

开头那段的前提是 GPU 有闲着的算力。这个前提会随着机器被填满而变弱，speculative decoding 的收益也跟着变弱。

![Reported speedup against batch size](blogs/images/specdec-batch-size.svg?v=1)

[有人直接量过](https://arxiv.org/abs/2310.18813)：同一套配置在 batch size 为 1 时是 2.73 倍，到 batch size 32 就只剩 1.31 倍，理由是"大 batch 本身已经把 GPU 算力占满了"。EAGLE-3 自己发表的表格是同样的形状：SGLang 上 batch 64 掉到 1.38 倍，vLLM 上 batch 56 掉到 1.01 倍。这本质上是一个延迟优化，只有机器空着的时候才看着像吞吐优化。

2026 年真正需要补的限定词是序列长度，也就是图上第四条线。[MagicDec](https://arxiv.org/abs/2408.11049) 指出，长上下文下 KV cache 的规模是 batch 乘序列长度，光把它读进来就足以让工作负载在大 batch 下依然访存受限，并报告 Llama-3.1-8B 在 batch 32 到 256 的区间里最高 2.51 倍。所以访存受限这个前提不是被"批处理"推翻的，是被"短序列加小缓存"推翻的。

收益也可能是负的。[llama.cpp 上的一个 issue](https://github.com/ggml-org/llama.cpp/issues/23752) 报告在 M1 Max 上，MTP speculative decoding 在所测的每一种配置下都是净亏损，从 25.3 tokens/s 掉到 19.3，理由是"Metal 上 draft 的前向开销超过了投机带来的收益"。这是单个用户的报告、状态还未确认，但它是个很具体的提醒：c 取决于具体的硬件和 kernel，而不是纸面上的参数量。

所以说到底，这个方向上的所有力气都被同一个不等式框着。让 drafter 以 target 为条件，并针对它真会面对的分布去训练，把 α 抬上去；让它一次前向出一整块，把 c 压下来；再让引擎去判断，机器什么时候已经满到不该继续做 speculation。那些发表出来的最大值，最好读作"这个方法在它最有利的那一种配置下能到多少"，而能被独立测出来的数字，在**小 batch 下**更接近 1.5 到 3 倍，随着机器被填满会一路滑向 1 倍。不过真正有意思的从来不是那个倍数，而是你拿到它的时候，模型本来要说的话，一个 token 都没变。
