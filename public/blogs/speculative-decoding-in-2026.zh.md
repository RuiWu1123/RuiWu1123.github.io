从一个大模型里生成一个 token，需要把模型的全部权重读一遍，却几乎不用它们做什么运算。batch size 为 1 的时候，GPU 的时间基本都花在等内存上，算力单元大半闲着。推测解码的全部机会就来自这个失衡：既然瓶颈是搬运而不是计算，那么一次检查好几个 token，代价并不比检查一个高多少。

于是可以下这样一个赌注。让某个便宜的东西先把接下来几个 token 猜出来，再把这些猜测一次性喂给大模型，让它同时对每个位置回答一个问题：这个 token 是不是我自己也会写出来的？凡是它点头的，你就白赚一个 token，省下了本该为它单独跑的那次前向。

让这件事超出"启发式技巧"范畴的，是这些猜测可以用一种方式采纳，使输出分布**精确地**保持不变。这个结果来自 [Leviathan、Kalman 和 Matias](https://arxiv.org/abs/2211.17192)（ICML 2023），以及同期独立完成的 [DeepMind 的 Chen 等人](https://arxiv.org/abs/2302.01318)，两篇都报了约 2–3 倍加速、输出与原模型逐字相同。此后所有的工作，本质上都是在想办法把"猜"这件事做得更好。下面所有的图都出自我为这篇文章写的模拟器，所以图里的数字是量出来的，不是我说出来的。

## 一、这条规则，以及它换来了什么

记 `p` 为目标模型在某个位置上的分布，`q` 为草稿在同一位置上的分布。草稿提出，目标决定：

```python
x = sample(q)                            # the draft proposes a token
if uniform() < min(1, p[x] / q[x]):      # the target checks it
    emit(x)
else:
    emit(sample(normalize(maximum(p - q, 0))))
```

真正承重的是两行。接受概率 `min(1, p[x]/q[x])` 的含义是：只要目标对这个 token 的偏好不低于草稿，就无条件留下；如果偏好更低，就按低多少的比例留。而一旦某个 token 被拒绝，替补**不是**从 `p` 里重采的，而是从**残差**里采的，也就是 `p` 当中没有被 `q` 覆盖到的那部分，重新归一化。

残差是大多数介绍会略过的一步，也恰恰是让整件事精确的那一步。按比例接受，等价于你从 `min(p, q)` 里采了个样，它比 `p` 恰好少了 `(p − q)⁺` 这一块；把被拒绝的那些从这块缺口里补采回来，少的正好被补上。

![The accept and reject rule](blogs/images/specdec-accept-rule.svg?v=1)

绿色是被直接留下的质量，加起来就是接受率 α。蓝色是残差要补回的部分。这样看，α 有一个干净的闭式：`α = Σ min(p, q) = 1 − TV(p, q)`，也就是一减去草稿与目标之间的总变差距离，这是 Leviathan 等人的推论 3.6。一个有一半时间和目标意见一致的草稿，就是一个分布距目标半个 TV 单位的草稿，跟它是什么架构无关。

"证明是精确的"这种话很容易点头附和，代码里也很容易出微妙的错，所以值得亲眼看一遍。我取了八个 token 上的目标分布 `p`，故意配一个与它总变差距离 0.34 的坏草稿 `q`，跑了两百万次单 token 推测步。

![Empirical distribution after two million speculative steps](blogs/images/specdec-lossless.svg?v=1)

草稿错得肉眼可见，众数都落在了错误的 token 上。输出却没有：实测输出与 `p` 的总变差是 0.00046，而两百万次采样的噪声地板约为 0.00071。草稿自己那 0.34 的误差不是被削小了，是彻底消失了。这正是推测解码在一众推理优化里显得特别的地方。量化和剪枝都是拿质量换速度，它什么也不换：草稿差，你损失的是速度，永远不是正确性。

接下来算账。一轮里草稿产出 γ 个 token，目标模型用一次前向把它们全部验证。第一次拒绝若发生在第 k 个位置，这一轮吐出 k+1 个 token：k 个被接受的，加上那个重采的替补；如果 γ 个全被接受，就吐出 γ+1 个，多出来的是从目标模型自己在最后一个位置上的分布里免费采的，因为这次验证前向已经把它算出来了。在论文声明的简化假设下（每个位置接受与否独立同分布、接受率为 α），一轮的期望产出是截断几何分布 `(1 − α^(γ+1))/(1 − α)`，我的模拟器在测过的每一组 α 和 γ 上都能复现到采样误差以内。α = 0.75、每轮草稿四个时，21 个 token 只用了 6 次目标前向，而不是 21 次：

![Target forward passes, autoregressive versus speculative](blogs/images/specdec-timeline.svg?v=1)

要注意这张图只数了目标模型的前向次数。这是展示机制时最诚实的口径，但作为加速比是偏乐观的，因为打草稿本身并不免费。

所以要把这笔成本放回去。记 `c` 为一次草稿前向相对一次目标前向的成本占比，墙钟加速就是

$$
\text{speedup} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}
$$

矛盾这下就摆出来了。把 γ 调大，分子涨得越来越慢，因为第 i 个草稿 token 只有在它前面全部被接受时才有意义；而分母是线性涨的。所以存在一个最优值，并且它随 α 移动：

![Speedup against draft length for several acceptance rates](blogs/images/specdec-speedup.svg?v=1)

α = 0.9 时最优是一次草稿七个，约 2.4 倍；α = 0.5 时最优是一次只草稿一个，约 1.25 倍，草稿更多反而更慢。真正要盯的数字是接受率而不是草稿模型的大小：α 同时决定了你能赢多少，以及你被允许玩得多激进。

有个流传很广的说法值得在这里就消灭掉。推论 3.9 说的是：只要 **α > c**，就一定存在某个 γ 能带来提升。按典型的 α 在 0.6 到 0.8 之间算，草稿只需要比目标快约 1.3 到 1.7 倍，而不是常被引用的十倍到三十倍；同一篇论文的 Table 4 里就摆着一个 c = 0.11 的配置，草稿只快约九倍，依然拿到 1.7 到 2.2 倍。已发表的设置大多落在 c ≈ 0.02–0.13，而且两篇原始论文谈甜点区时用的都是参数量，不是延迟比。

## 二、草稿器怎么设计

上面这些一直把草稿当成一个产出 `q` 的黑盒。既然真正起作用的只有 α 和 c 两个量，那么每一种草稿器设计都是同一个平面上的一步棋，而这个平面值得直接摆出来看：

![The design space of drafters](blogs/images/specdec-design-space.svg?v=1)

虚线是 α = c。两个箭头是所有人手里仅有的两个杠杆：往上推，让草稿更常猜中；往左推，让草稿更便宜。这个方向上几乎每篇论文都是在拉其中一个，而有意思的那些会发现两个杠杆之间是有耦合的。

最早的提议是同系列里的另一个更小的模型。它不需要改动目标模型，任何一对都能配，但你得正好有一个在相似数据上训过的小模型，而它的 α 是多少就是多少。它的问题是结构性的：一个独立的模型必须从零重建上下文，而目标模型内部早就把这份上下文编码得好好的了。

所以主线就把独立的小模型换成了一个读取目标模型内部状态的头。EAGLE 让一个小的自回归头以目标模型的隐藏特征为条件，等于是带着目标自己对上下文的理解去猜，而不是靠自己那份更弱的理解。这纯粹是在拉 α，而且之所以可行，是因为那些特征本来就已经算出来了，所以这个头可以做得极小。

第三族转而攻 c，而且攻的方式在公式里一眼可见。如果 γ 个草稿 token 要靠自回归产出，那分母里的 `c` 其实是 `γ · c_单次`，于是无论草稿器多好，最优 γ 都被压得很低。并行草稿器打断了这个耦合：一次前向产出一整块，`c` 从此和 γ 完全脱钩。[DFlash](https://arxiv.org/abs/2602.06036)（Chen、Liang、Liu，UC San Diego 的 Z Lab，ICML 2026）用的是一个以目标模型上下文特征为条件的小块扩散模型，这个选择很自然，因为扩散天生就是跨位置并行的。

还有一族完全不学习。SuffixDecoding 在 prompt 和历史输出上建一棵后缀树，靠匹配出草稿，`c` 接近于零，位置在这个平面的最左端。它的 α 则完全取决于工作负载：在开放式散文上近乎无用，而在 agentic 这类模型大段引用自己先前输出的场景里好用得不太讲道理。

## 三、草稿器怎么训练

把 α 往上推是个训练问题，而它有一个占主导地位的失败模式：草稿器被训练在一个它推理时根本不会遇到的分布上。

朴素的目标函数是：给定一段真实前缀，让草稿头预测目标模型的下一个 token。可推理时草稿器要连着往前跑好几步，每一步依据的是**它自己**先前的猜测，而那些猜测有时是错的。到第三个位置上，它被要求续写的是一段训练里从未出现过的前缀。这就是普通的 exposure bias，表现出来就是接受率沿着块往后掉。

[EAGLE-3](https://arxiv.org/abs/2503.01840)（Li、Wei、Zhang、Zhang；北大、微软研究院、滑铁卢大学与 Vector Institute；NeurIPS 2025）用作者称为 training-time test 的做法修它：训练时就把多步打草稿的过程模拟一遍，让这个头面对的是它推理时真正会遇到的分布。同一篇论文还做了第二个改动，放弃预测特征、改成直接预测 token，并报告这个组合让草稿器能持续从更多训练数据中获益，而原来那种预测特征的形式做不到。

并行草稿器有一个相关但不同的毛病。既然块内每个位置都是独立预测的，就没有任何东西阻止第 4 个位置和第 3 个位置自相矛盾，于是越靠近块尾，一致性越低。而这条衰减曲线的形状，比它看上去更要紧：

![Acceptance along the block](blogs/images/specdec-suffix-decay.svg?v=1)

一轮的产出是 `1 + Σ_k Π_{i≤k} α_i`，是一串**连乘**，所以靠前的位置权重远大于靠后的，一条往下掉的尾巴造成的损失，比"平均接受率"这个数字暗示的要大。上图三条曲线里，衰减那条整块的平均接受率并不难看，产出却只有每轮 3.81 个 token，而平坦那条是 4.33。

修这条衰减正是 [DSpark](https://arxiv.org/abs/2607.05147)（Cheng 等人，北京大学与 DeepSeek-AI）加的东西：在并行主干之上叠一个极轻的序列头，把块内位置之间的依赖重新注入回去。它的 Markov 变体是把一阶转移矩阵做低秩分解，说白了就是在并行模型给出的边缘 logits 上加一个秩为 r 的偏置，用来重建一部分联合分布。把衰减压平，比把平均值抬高更值钱，这也是上图第三条曲线能到 5.32 的原因。

## 四、验证怎么设计

验证这一步有三年时间都是一条统一施加的固定规则，而现在剩下的空间有相当一部分就在这儿。

第一个观察是：没有任何东西规定草稿必须是一条链。如果草稿器在同一个位置上给出好几个候选，目标模型完全可以在同一次前向里把它们全查了，反正这次前向本来就是访存受限的。验证规则可以自然推广：先试第一个候选，被拒了就更新残差、再拿第二个去试。

![Chain versus tree, and acceptance against candidate count](blogs/images/specdec-tree-verify.svg?v=1)

还是同样的 p 和 q，一个候选时接受率是 66%，六个候选时是 87%。而这里最出人意料的是：这些**依然是精确无损的**。多给几个猜测并不会让输出有偏，只是让你更少地退回去用残差。这就是树形草稿的思路，而 EAGLE-2 又往前推了一步，让树的形状随时变化而不是固定的，把候选预算花在草稿器最没把握的地方。

第二个观察是：验证长度不必是常数。一段长草稿只有在它大概率能活下来的时候才值得验证；而在高负载下，目标模型的 batch 容量是一种被争抢的资源，投机正在和真实请求抢它。DSpark 的另一半就是按请求调度验证长度，依据是一个校准过的前缀存活概率估计，再加上引擎的吞吐画像，好让繁忙的服务器停止把目标模型的容量花在多半会被丢弃的投机上。

第三个观察不太舒服：你可以验证得不那么严格，然后跑得更快。[Medusa](https://arxiv.org/abs/2401.10774)（Cai 等人，ICML 2024）在目标模型上挂若干个解码头，验证用的是它称为 typical acceptance 的做法：只要目标模型给这个 token 的概率越过一个与熵相关的阈值就接受。论文对这笔交易是挑明了说的，不是含糊过去："我们确认，通常并没有必要匹配原模型的分布"，附录里还有一句更直白的："我们并不坚持输出与语言模型分布之间的精确对应"。它留了一个可调的旋钮，调大就是用更激进的接受换速度。

值得知道的是，开山那篇论文先到过这里，然后选择了相反的方向。Leviathan 等人的附录 A.5 描述的正是这样一种松弛，取名 lenience，并报告它在 T5-XXL 上能到 5 倍而严格版本是 3 倍，然后把它隔离了：全文其余部分一律使用最严格的算法，不允许任何 lenience。同一个想法，一篇当污染物，另一篇当默认值。温度为 0 时这个区别会塌缩，因为 typical acceptance 会退化成贪心。但它确实意味着"无损"这个词得读仔细：它是关于那条拒绝规则的一个精确断言，一个改了规则的方法并不自动继承它。

## 五、收益会跑到哪里去

开头那段的前提是 GPU 有闲置的算力。这个前提会随着机器被填满而减弱，推测解码的收益也跟着减弱。

![Reported speedup against batch size](blogs/images/specdec-batch-size.svg?v=1)

[Su、Giannoula 和 Pekhimenko](https://arxiv.org/abs/2310.18813) 直接量过：同一套配置在 batch size 为 1 时是 2.73 倍，到 batch size 32 就只剩 1.31 倍，原因是"大 batch 本身已经把 GPU 算力占满了"。EAGLE-3 自己发表的表格是同样的形状：SGLang 上 batch 64 降到 1.38 倍，vLLM 上 batch 56 降到 1.01 倍。这本质上是一个延迟优化，只有机器空着的时候才看起来像吞吐优化。

2026 年真正需要补的限定词是序列长度，也就是图上第四条线。[MagicDec](https://arxiv.org/abs/2408.11049) 指出，长上下文下 KV cache 的规模是 batch 乘序列长度，光是把它读进来就足以让工作负载在大 batch 下依然访存受限，并报告 Llama-3.1-8B 在 batch 32 到 256 的区间里最高 2.51 倍。所以访存受限这个前提不是被"批处理"推翻的，是被"短序列加小缓存"推翻的。

收益也可能是负的。[llama.cpp 上的一个 issue](https://github.com/ggml-org/llama.cpp/issues/23752) 报告在 M1 Max 上，MTP 推测解码在所测的每一种配置下都是净亏损，从 25.3 tokens/s 掉到 19.3，理由是"Metal 上草稿的前向开销超过了投机带来的收益"。这是单个用户的报告、状态还是未确认，但它是个很具体的提醒：c 是你的硬件和 kernel 的属性，不是纸面上参数量的属性。

## 六、怎么读 2026 年的这些数字

近期工作附带的加速数字需要比平时更小心去读，报告值和复现值之间的差距一直很大。

EAGLE-3 的头条是"最高 6.5 倍"，那是某张表里的某一格，条件是温度 0、batch size 1。独立测量落得低得多：[Red Hat 的 vLLM 评测](https://developers.redhat.com/articles/2025/07/01/fly-eagle3-fly-faster-inference-vllm-speculative-decoding)在 A100 上报最高 2.5 倍，并指出它在翻译任务上表现很差；Thoughtworks 在 H100 上的复现测到 1.25 倍，而论文对应位置是 1.32 倍。DFlash 的摘要说在 Qwen3-8B 上超过 6 倍，而它自己那张 benchmark 表的平均值是 4.86 倍，对话基准是 2.75 倍；Baseten 独立实现的一版在 B200、并发 16 下报约 3 倍。另外值得注意，DFlash 拿来对比的 EAGLE-3 用的是第三方 checkpoint，因为 EAGLE-3 官方没有 Qwen3 的 checkpoint，而 DFlash 自己的草稿器是作者训练的，所以那个差距里有多少来自架构、有多少来自训练数据，并不清楚。

DSpark 那个 60–85% 最需要谨慎，而这一点论文自己就说了，这值得记一功。这个区间只对应 V4-Flash 这一个变体，对比的是 DeepSeek 自家先前的生产基线，测量场景是 DeepSeek 自己的线上真实流量，硬件未披露，而且数字是从一条拟合出来的性能前沿曲线上读出来的，不是受控 A/B。在它最大的那个吞吐数字上，论文明确表示不应把它理解为一个有代表性的加速倍数。目前没有独立复现，而且从外部结构上也做不到：[DeepSpec](https://github.com/deepseek-ai/DeepSpec) 这个 MIT 许可的仓库确实包含 DSpark、DFlash 和 EAGLE-3 真实可用的训练与评测代码，但不包含那套生产推理引擎。LMSYS 在 SGLang 上的集成说得很克制，说自己复现的是机制和曲线形状，不是那些数字本身。

这些都不意味着这些工作是虚的。它意味着诚实的总结是：在能被独立测量的条件下，推测解码可靠地交付大约 1.5 到 3 倍；上限由接受率和你的 GPU 本来就有多满共同决定；而那些发表出来的最大值，最好理解成"这个方法在它最有利的那一种配置下能做到什么"。

过去一年真正变了的，不是数字的大小，而是力气花在哪儿。草稿不再是一个你碰巧手头有的小模型，而是一个与目标模型协同设计、读取它内部状态、针对它真正会面对的分布训练、并且越来越多地一次前向就产出一整块的组件。而验证也不再是一条固定规则，正在变成调度器需要按请求去权衡的东西。这两件事都是第一节那点算术的必然结果：一切都是在想办法抬高 α 而不抬高 c。
