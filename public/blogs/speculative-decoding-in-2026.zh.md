从一个大模型里生成一个 token，需要把模型的全部权重读一遍，却几乎不用它们做什么运算。batch size 为 1 的时候，GPU 的时间基本都花在等内存上，算力单元大半闲着。推测解码的全部机会就来自这个失衡：既然瓶颈是搬运而不是计算，那么一次检查好几个 token，代价并不比检查一个高多少。

于是可以下这样一个赌注。让某个便宜的东西先把接下来几个 token 猜出来，然后把这些猜测一次性喂给大模型，让它同时对每个位置回答一个问题：这个 token 是不是我自己也会写出来的？凡是它点头的，你就白赚一个 token，省下了本该为它单独跑的那次前向。

让这件事超出"启发式技巧"范畴的，是这些猜测可以用一种方式采纳，使输出分布**精确地**保持不变。不是近似不变，也不是"实践中差不多"，而是吐出来的 token 严格服从大模型独自生成时的那个分布。这个结果来自 [Leviathan、Kalman 和 Matias](https://arxiv.org/abs/2211.17192)（ICML 2023），以及同期独立完成的 [DeepMind 的 Chen 等人](https://arxiv.org/abs/2302.01318)；两篇分别在各自模型上报了约 2–3 倍的加速，输出与原模型逐字相同。

这篇文章讲的是它为什么成立、真正能拿到多少收益，以及 2026 年的前沿长什么样。下面所有的图都出自我为这篇文章写的一个模拟器，不是画图工具，所以图里的数字是量出来的，不是我说出来的。

## 一、让它精确的那条规则

记 `p` 为目标模型在某个位置上的分布，`q` 为草稿模型在同一位置上的分布。草稿提出一个 token，目标模型决定要不要留：

```python
x = sample(q)                            # the draft proposes a token
if uniform() < min(1, p[x] / q[x]):      # the target checks it
    emit(x)
else:
    emit(sample(normalize(maximum(p - q, 0))))
```

真正承重的是两行。接受概率 `min(1, p[x]/q[x])` 的含义是：只要目标模型对这个 token 的偏好不低于草稿，就无条件留下；如果偏好更低，就按低多少的比例留。而一旦某个 token 被拒绝，替补**不是**从 `p` 里重采的，而是从**残差**里采的，也就是 `p` 当中没有被 `q` 覆盖到的那部分，重新归一化成一个分布。

残差是大多数介绍会略过的一步，也恰恰是让整件事精确的那一步。按比例接受，等价于你从 `min(p, q)` 里采了个样，它比 `p` 恰好少了 `(p − q)⁺` 这一块；把被拒绝的那些从这块缺口里补采回来，少的正好被补上。

![The accept and reject rule](blogs/images/specdec-accept-rule.svg?v=1)

绿色是被直接留下的质量，它加起来就是接受率 α。蓝色是残差需要补回的部分。这样看，α 有一个干净的闭式：`α = Σ min(p, q) = 1 − TV(p, q)`，也就是一减去草稿和目标之间的总变差距离，这是 Leviathan 等人的推论 3.6。一个有一半时间和目标意见一致的草稿，就是一个分布距离目标半个 TV 单位的草稿，跟它是什么架构毫无关系。

## 二、验证一下它是不是真的无损

"证明是精确的"这种话很容易点头附和，代码里也很容易出微妙的错，所以值得亲眼看一遍。我取了一个八个 token 上的目标分布 `p`，故意配一个很差的草稿 `q`（与 `p` 的总变差距离 0.34，也就是有三分之一的时间在胡说），然后跑了两百万次单 token 的推测步。

![Empirical distribution after two million speculative steps](blogs/images/specdec-lossless.svg?v=1)

草稿错得肉眼可见：众数落在了错误的 token 上，另外几个的权重也偏得很离谱。输出却没有。实测输出与 `p` 的总变差是 0.00046，而两百万次采样的噪声地板大约是 0.00071。草稿自己那 0.34 的误差不是被削小了，是彻底消失了。

这正是推测解码在一众推理优化里显得特别的地方。量化拿质量换速度，剪枝拿质量换速度，而它什么也不换：草稿差，你损失的是速度，永远不是正确性。草稿要是差到离谱，α 就会塌到接近 0，绝大多数提议被拒，你白花了那些草稿的前向开销。但你没有改变答案。

## 三、到底能赚多少

一轮里草稿产出 γ 个 token，目标模型用一次前向把它们全部验证。如果第一次拒绝发生在第 k 个位置，这一轮吐出 k+1 个 token：k 个被接受的，加上那个重采的替补。如果 γ 个全被接受，就吐出 γ+1 个，多出来的那个是从目标模型自己在最后一个位置上的分布里免费采的，因为这次验证前向已经把它算出来了。

在论文明确声明的简化假设下（每个位置的接受与否独立同分布、接受率为 α），一轮的期望产出是一个截断几何分布：

$$
\mathbb{E}[\text{tokens per round}] = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}
$$

我的模拟器在测过的每一组 α 和 γ 上都能把这个公式复现到采样误差以内，这也顺带确认了代码和代数没有各说各话。下面是它实际跑起来的样子，每轮草稿四个，α = 0.75：

![Target forward passes, autoregressive versus speculative](blogs/images/specdec-timeline.svg?v=1)

同样 21 个 token，自回归用了 21 次目标前向，推测解码用了 6 次，平均每次前向产出 3.5 个 token。要注意这张图只数了目标模型的前向次数，这是展示机制时最诚实的口径，但作为加速比是偏乐观的，因为打草稿本身并不免费。

把草稿的成本放回去。Leviathan 等人定义 `c` 为一次草稿前向相对于一次目标前向的成本占比，于是墙钟加速为

$$
\text{speedup} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}
$$

矛盾这下就摆出来了。把 γ 调大，分子涨得越来越慢，因为第 i 个草稿 token 只有在它前面全部被接受时才有意义；而分母是线性涨的。所以存在一个最优值，并且它随 α 移动：

![Speedup against draft length for several acceptance rates](blogs/images/specdec-speedup.svg?v=1)

α = 0.9 时，最优是一次草稿七个，能拿到约 2.4 倍。α = 0.5 时，最优是一次只草稿一个，约 1.25 倍，草稿更多反而更慢。这就是为什么真正要盯的数字是接受率而不是草稿模型的大小：α 同时决定了你能赢多少，以及你被允许玩得多激进。

盈亏平衡的条件从同一个公式里就能读出来，值得说准确，因为围绕它长出了一个流传很广的说法。Leviathan 等人的推论 3.9 说的是：只要 **α > c**，就一定存在某个 γ 能带来提升。按典型的 α 在 0.6 到 0.8 之间算，草稿只需要比目标快大约 1.3 到 1.7 倍，而不是常被引用的十倍到三十倍。他们自己的 Table 4 里就摆着一个 c = 0.11 的配置，草稿只快约九倍，依然拿到 1.7 到 2.2 倍。已发表的设置大多落在 c ≈ 0.02–0.13，而且两篇原始论文谈甜点区时用的都是参数量（比目标小约两个数量级），不是延迟比。你在权衡的是 α 和 c 的关系，没有哪个固定的速度倍数能替你拍板。

## 四、收益会跑到哪里去

开头那段的前提是 GPU 有闲置的算力。这个前提会随着机器被填满而减弱，推测解码的收益也跟着减弱。

[Su、Giannoula 和 Pekhimenko](https://arxiv.org/abs/2310.18813) 直接量过这件事：同一套自适应推测解码，batch size 为 1 时是 2.73 倍，到 batch size 32 就只剩 1.31 倍，原因是"大 batch 本身已经把 GPU 算力占满了"。EAGLE-3 自己发表的表格从另一个方向印证了同样的形状：在 SGLang 上 batch size 64 时降到 1.38 倍，在 vLLM 上 batch size 56 时降到 1.01 倍。这本质上是一个延迟优化，只有在机器空着的时候才看起来像吞吐优化。

2026 年真正需要补的限定词是序列长度。[MagicDec](https://arxiv.org/abs/2408.11049) 指出，长上下文下 KV cache 的规模是 batch 乘序列长度，光是把它读进来就足以让工作负载在大 batch 下依然是访存受限的，并报告 Llama-3.1-8B 在 batch 32 到 256 的区间里最高 2.51 倍。所以访存受限这个前提不是被"批处理"推翻的，是被"短序列加小缓存"推翻的。

收益也可能是负的，而且比宣传里显得容易碰到。[llama.cpp 上的一个 issue](https://github.com/ggml-org/llama.cpp/issues/23752) 报告在 M1 Max 上，MTP 推测解码在所测的每一种配置下都是净亏损，从基线的 25.3 tokens/s 掉到 19.3，理由是"Metal 上草稿的前向开销超过了投机带来的收益"。这是单个用户的报告、状态还是未确认，但它是个很具体的提醒：c 是你的硬件和 kernel 的属性，不是纸面上模型大小的属性。

## 五、草稿从哪里来

上面这些一直把草稿当成一个产出 `q` 的黑盒。而过去三年的工作几乎全都在研究这个盒子里该装什么，大致可以分成几族。

最早的提议也是最直白的：同系列里的另一个更小的模型。它不需要改动目标模型，任何一对模型都能配，但你得正好有一个在相似数据上训过的小模型，而它的 α 是多少就是多少。

学界的主线把独立的小模型换成了一个读取目标模型内部状态的头。EAGLE 让一个小的自回归头以目标模型的隐藏特征为条件，等于是带着目标模型自己对上下文的理解去猜。[EAGLE-3](https://arxiv.org/abs/2503.01840)（Li、Wei、Zhang、Zhang；北大、微软研究院、滑铁卢大学与 Vector Institute；NeurIPS 2025）做了两个定义了当前基线的改动：放弃预测特征、改成直接预测 token；以及加入作者称为 training-time test 的做法，在训练时就模拟多步草稿的过程，让草稿头面对的是它推理时真正会遇到的分布，而不是只练"预测下一个"。

第三族干脆放弃了顺序打草稿。如果 γ 个草稿 token 要靠自回归产出，那草稿成本 `c` 就随 γ 线性增长，上面那条曲线的最优点也就压得很低。并行草稿器一次前向产出一整块，`c` 从此和 γ 脱钩。[DFlash](https://arxiv.org/abs/2602.06036)（Chen、Liang、Liu，UC San Diego 的 Z Lab，ICML 2026）用的是一个以目标模型上下文特征为条件的小块扩散模型，这个选择很自然，因为扩散天生就是跨位置并行的。代价是块内各个位置是各自独立预测的，彼此可能对不上，于是越靠近块尾接受率越低。

修这个衰减正是 [DSpark](https://arxiv.org/abs/2607.05147)（Cheng 等人，北京大学与 DeepSeek-AI）加的东西：在并行主干之上再叠一个极轻的序列头，把块内位置之间的依赖重新注入进去。它的 Markov 变体是把一阶转移矩阵做低秩分解，说白了就是在并行模型给出的边缘 logits 上加一个秩为 r 的偏置，用来重建一部分联合分布。与之配套的是按请求调度验证长度，依据是对前缀存活概率的估计，这样在高负载下引擎就不会把目标模型的 batch 容量花在多半会被拒的投机上。

最后还有一族完全不学习的草稿器。SuffixDecoding 在 prompt 和历史输出上建一棵后缀树，靠匹配来出草稿。在 agentic 这类模型大段引用自己先前输出或引用 prompt 的场景里，这个没有任何参数的东西好用得不太讲道理。

## 六、大家悄悄放弃了的那个"精确"

第一节那个保证，只对那条按原样写出来的拒绝规则成立。而好几个流行方法用的并不是那条规则。

[Medusa](https://arxiv.org/abs/2401.10774)（Cai 等人，ICML 2024）在目标模型上挂若干个解码头，验证时用的是它称为 typical acceptance 的做法：只要目标模型给这个 token 的概率越过一个与熵相关的阈值就接受。论文对这笔交易是挑明了说的，不是含糊过去："我们确认，通常并没有必要匹配原模型的分布"，附录里还有一句更直白的："我们并不坚持输出与语言模型分布之间的精确对应"。它留了一个可调的旋钮，调大就是用更激进的接受换速度。

值得知道的是，开山那篇论文先到过这里，然后选择了相反的方向。Leviathan 等人的附录 A.5 描述的正是这样一种松弛，取名 lenience，并报告它在 T5-XXL 上能到 5 倍而严格版本是 3 倍，然后把它隔离了：全文其余部分一律使用最严格的算法，不允许任何 lenience。同一个想法，一篇当成污染物，另一篇当成默认值。

这些都不说明 Medusa 有什么问题，而且在温度为 0 时这个区别会塌缩掉，因为 typical acceptance 会退化成贪心。它只是意味着"无损"这个词得读仔细：它是关于那条拒绝规则的一个精确断言，一个改了规则的方法并不自动继承它。

## 七、怎么读 2026 年的这些数字

近期工作附带的加速数字需要比平时更小心去读，报告值和复现值之间的差距一直很大。

EAGLE-3 的头条是"最高 6.5 倍"，那是某张表里的某一格，条件是温度 0、batch size 1。独立测量落得低得多：[Red Hat 的 vLLM 评测](https://developers.redhat.com/articles/2025/07/01/fly-eagle3-fly-faster-inference-vllm-speculative-decoding)在 A100 上报最高 2.5 倍，并指出它在翻译任务上表现很差；Thoughtworks 在 H100 上的复现测到 1.25 倍，而论文对应位置是 1.32 倍。DFlash 的摘要说在 Qwen3-8B 上超过 6 倍，而它自己那张 benchmark 表的平均值是 4.86 倍，对话基准（MT-Bench）是 2.75 倍；Baseten 独立实现的一版在 B200、并发 16 下报约 3 倍。另外值得注意，DFlash 拿来对比的 EAGLE-3 用的是第三方 checkpoint，因为 EAGLE-3 官方没有 Qwen3 的 checkpoint，而 DFlash 自己的草稿器是作者训练的，所以那个差距里有多少来自架构、有多少来自训练数据，并不清楚。

DSpark 那个 60–85% 最需要谨慎，而这一点论文自己就说了，这值得记一功。这个区间只对应 V4-Flash 这一个变体，对比的是 DeepSeek 自家先前的生产基线，测量场景是 DeepSeek 自己的线上真实流量，硬件未披露，而且数字是从一条拟合出来的性能前沿曲线上读出来的，不是受控 A/B。在它最大的那个吞吐数字上，论文明确表示不应把它理解为一个有代表性的加速倍数。目前没有独立复现，而且从外部结构上也做不到：[DeepSpec](https://github.com/deepseek-ai/DeepSpec) 这个 MIT 许可的仓库确实包含 DSpark、DFlash 和 EAGLE-3 真实可用的训练与评测代码，但不包含那套生产推理引擎。LMSYS 在 SGLang 上的集成说得很克制，说自己复现的是机制和曲线形状，不是那些数字本身。

这些都不意味着这些工作是虚的。它意味着关于这个领域，诚实的总结是：在能被独立测量的条件下，推测解码可靠地交付大约 1.5 到 3 倍；上限由接受率和你的 GPU 本来就有多满共同决定；而那些发表出来的最大值，最好理解成"这个方法在它最有利的那一种配置下能做到什么"。

过去一年真正变了的，不是数字的大小，而是力气花在哪儿。草稿不再是一个你碰巧手头有的小模型，而是一个与目标模型协同设计、读取它内部状态、并且越来越多地一次前向就产出一整块的组件。而验证这一步，三年来一直是一条统一施加的固定规则，如今正在变成调度器需要按请求去权衡的东西。这两件事都是第三节那点算术的必然结果：一切都是在想办法抬高 α 而不抬高 c。
