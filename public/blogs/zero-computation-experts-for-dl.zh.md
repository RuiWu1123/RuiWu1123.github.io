[MoE 那篇文章](#/blog?id=moe-field-guide-for-dl) 讲了路由、门控函数、负载均衡、粒度、latent 压缩，这些改的都是"用哪些专家"或者"每个专家参数值多少算力"。但它们都有一个共同前提：top-K 是固定的——不管这个 token 是个标点符号还是一步真正难的推理，激活的专家数量都一样。这篇文章讲一个不一样的思路：让专家池里的一部分"专家"根本不做计算，这样路由器就可以把一个不需要真正计算的 token，分配到一个几乎不花钱的专家槽位上。这个想法的脉络不长——两篇论文，前后隔了一年半，然后一家公司把它用到了万亿参数规模的模型上。

## 1. 问题：top-K 对所有 token 一视同仁

标准的 MoE 层给每个 token 分配同样数量的专家 K，而且这 K 个专家不管这个 token 实际需不需要，都要老老实实跑一遍完整的前向计算。一个句尾的句号，和一个真正有歧义的词，付出的计算量完全一样。这是真实的浪费：不是每个 token 都需要 K 个专家份的计算量，而给所有 token 强加一个统一的预算，结果要么是 K 定得够大来照顾难 token，白白浪费在简单 token 上；要么是 K 定得够小来照顾简单 token，让难 token 吃不饱。

零计算专家直接针对这个问题：在专家池里放一个几乎不花钱的选项，让路由器可以把不需要真正计算的 token 分过去。

## 2. "零计算"具体指什么

零计算专家和普通 FFN 专家待在同一个路由池里，被同样的 top-K 机制选中。区别在于选中之后发生了什么：它不会跑一遍前向计算，而是做几种近乎免费的操作中的一种，这个槽位对 token 的贡献几乎不花钱。

```python
def zero_computation_expert(x, kind, c=None):
    if kind == "zero":
        return 0        # 丢弃：什么贡献都没有
    elif kind == "copy":
        return x         # 跳过：把输入原样传出去
    elif kind == "constant":
        return c         # 替换：一个和 x 无关的、可训练的小向量
```

这和专家剪枝是两件不同的事。剪枝是把一个专家从模型里彻底删掉；零计算专家则一直留在路由池里，是路由器在每个 token、每一层、每一步都可以选择的一个常驻选项。

## 3. 起点：AdaMoE 的 null expert

**AdaMoE**（Zeng et al.，2024 年 6 月提交，EMNLP 2024 Findings）是这个想法第一次被明确提出的地方。标准 MoE 路由强迫每个 token 都走同样的 top-K，论文指出这件事本身就站不住脚：`<EOS>` 这种 token 和 `apple` 这种 token，显然不需要同样数量的专家。AdaMoE 的做法很小、几乎是一点改动：在专家池里加入固定数量的 **null expert**（空专家），同时把 K 调大给它们腾出位置。null expert 不消耗任何 FLOPs。路由器不需要给每个 token 强制分配固定数量的 null expert——一个负载均衡损失只控制 null expert 在整个 batch 里的**平均**使用率，于是不同 token 最终用到的真实专家数量会不一样，而这个差异不是靠任何显式规则强加的。

用在 Mixtral-8x7B 的微调上，AdaMoE 在 ARC-C 上把平均 FLOPs 降低了 14.5%，准确率反而提高了 1.69%；在六个 benchmark 上平均 FLOPs 降低 15.21%，效果依然领先微调后的 baseline。这个机制足够小，可以直接接到一个已经训练好的 MoE 模型上，不需要从头预训练。

## 4. 把它系统化：MoE++ 的三种操作

**MoE++**（Jin et al.，2024 年 10 月提交，ICLR 2025 Oral）把 AdaMoE 的 null expert 当成一个更大类别里的一个特例。MoE++ 不只定义一种零计算专家，而是三种，分别对应三种近乎免费的操作：**zero expert**（丢弃输入，什么贡献都没有——和 AdaMoE 的 null expert 是同一个操作）、**copy expert**（把输入原样传出去，相当于这个槽位变成了一条免费的残差连接）、**constant expert**（用一个可训练的小向量替换输入，和这个 token 具体是什么无关）。

之所以要三种而不是一种，是因为它们分别覆盖了"这个 token 到底需要多少"这个判断下的不同情况：一个真的什么都不需要的 token，交给 zero expert；一个当前表示已经够用的 token，交给 copy expert；一个不管内容是什么、都需要一个固定的、学出来的调整量的 token，交给 constant expert。

MoE++ 还解决了一个朴素版零计算专家会遇到的部署问题。真正的 FFN 专家要拆到不同加速卡上，token 要经过互联网络才能到达自己被分配的专家（[分布式训练那篇文章](#/blog?id=distributed-training-for-dl) 讲了这种通信在大规模下为什么昂贵）。零计算专家的参数量几乎为零，所以 MoE++ 直接把它们的完整副本放在每一张 GPU 上。一个被路由到零计算专家的 token，永远不需要离开它当前所在的设备，也永远不会造成专家并行的负载不均衡，因为这些"专家"根本没有真正的容量会溢出。

在同等模型规模下，MoE++ 比 vanilla MoE 的专家前向吞吐量高 1.1–2.1 倍，效果还更好——让简单 token 少用几个真正的 FFN 专家，腾出来的容量能让真正的专家在需要它们的 token 上专精得更彻底。

## 5. 走向生产：LongCat-Flash 和 LongCat-2.0

AdaMoE 和 MoE++ 都是在远低于前沿模型规模上的学术验证。**LongCat-Flash**（美团，技术报告 2025 年 9 月提交，560B 参数）是第一个把零计算专家用进从头预训练、生产级规模模型的公开案例，**LongCat-2.0**（2026 年 6 月，1.6T 参数）在更大的规模上延续了同一个设计。

机制上和 MoE++ 的 zero expert 是同一个想法，但美团给的叙述角度不太一样：与其说"路由器挑了几个真专家和几个不干活的专家"，不如说是**动态计算预算分配**。一个 token 的激活参数量不再是由 K 单独决定的固定数字，而是一个区间，具体落在区间哪个位置，取决于路由器判断这个 token 到底需要多少真实专家容量。LongCat-Flash 公布的区间是每 token 激活 18.6B–31.3B 参数（平均 27B）；LongCat-2.0 是 33B–56B。一个简单 token——标点、重复模式——可以大部分路由到零计算专家，激活量落在区间低端；路由器判断更难的 token 会调用更多真实专家容量，激活量落在区间高端。

训练过程中让这个平均值稳定在目标区间内，不是自动发生的——训练目标本身并不能保证这个平均值会停在设计者想要的位置，而不是往任何一个极端漂移。LongCat-Flash 用一个 **PID controller** 持续调节朝向或者远离零计算专家的路由 bias，这和 DeepSeek-V3 用于负载均衡的那种逐专家 bias 机制是同一类东西（[MoE 那篇文章第 3 节](#/blog?id=moe-field-guide-for-dl) 讲过），区别只是这里追踪的目标是平均激活参数量，而不是每个专家的负载。

## 6. 零散的后续工作

有几篇更新的论文在不同方向上延伸了这个想法，还没形成统一的第二波。一条路子是把 zero/copy/constant 这套框架直接搬到多模态模型上，而不只是纯文本模型。另一条路子完全绕开了 MoE 训练的框架：不从头训练一个带零计算专家的模型，而是把一个已经训练好的 dense 模型的 MLP 做确定性分解，拆成一组静态分支，其中一部分分支最终几乎什么都不做，全程不需要额外训练。这些工作应该和另一条更早的 MoE 效率路线区分开——专家剪枝，按专家实际被使用的频率排序，直接删掉用得最少的那些。剪枝和零计算专家都是在减少 MoE 模型里被浪费掉的计算，但方向正好相反：剪枝是把专家池永久缩小，零计算专家是保持专家池的名义大小不变，让路由器逐个 token 地选择退出。

## 7. 还没解决的问题

最直接的一个开放问题是训练时的激励本身：如果路由到零计算专家不花钱，路由到真正的 FFN 专家在训练时也不会给模型额外的损失（默认情况下 loss 里没有算力成本这一项），那是什么阻止路由器把所有 token 都路由到免费选项、以此把 language-modeling loss 降到最低？LongCat 的 PID controller 是生产环境里给出的具体答案——通过调节路由 bias，把平均激活参数量控制在目标区间内——但这是一个对症状做反应的控制机制，不是对底层激励结构本身的改变。公开材料里没有更强的说法，说这个激励问题已经被解决，而不是被控制住。

另一个开放问题是这个想法怎么和 LatentMoE 组合。LatentMoE 是 MoE 那篇文章第 8 节讲的机制，它压缩的是**每一个**专家的计算成本，把计算搬到一个压缩过的 latent 空间里，而不是改变有多少专家在跑。这两者回答的是同一个总计算量等式里的两个不同部分——LatentMoE 降低每个激活专家的成本，零计算专家降低真正需要激活的专家数量——两者之间没有互斥的地方。目前还没有公开报告在同一个模型里把两者结合起来。

从概念上讲，零计算专家最接近的祖先根本不在 MoE 这条脉络里——是 **Mixture-of-Depths**（2024），它让 token 基于一个学出来的、逐 token 的决策，直接跳过整个 transformer block。零计算专家是同一个想法，只是作用在单个 MoE 层内部的专家维度上，而不是整个网络的深度维度上。
